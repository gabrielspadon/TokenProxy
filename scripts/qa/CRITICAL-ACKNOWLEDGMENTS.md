# Critical transaction acknowledgment evidence

Every real adapter records critical writes through `criticalAckJournal.js`. Ordinary writes and budget/accounting behavior keep their existing transaction paths. The native controller uses SQLite FULL or stronger synchronous mode; sql.js publishes its complete snapshot through its existing file and directory barriers.

The boundary writes a durable external intent before invoking the callback, inserts an immutable marker and hash-chain head in the same database transaction as the mutation, commits/publishes the database, then publishes an external receipt before returning. Receipts live beside the database in `<databaseFile>.critical-acks`, with private directory/file permissions, complete-inode publication, exclusive sequence filenames, file fsync and POSIX directory fsync. No SQL, parameters, credentials, or business values enter the journal. `mutationChanges` counts connection-local changes made by the callback, including triggers, before the marker insert. It does not identify or hash mutable business rows.

The scope is `durable-before-return`. A crash after receipt publication but before JavaScript return can leave an eligible receipt for a call that never returned. The retained receipt set therefore covers every possible successful return conservatively; `callerObserved` is always null. Neither a file hash nor a marker proves delivery to an HTTP caller.

After a durable commit, a receipt or synchronous-mode restoration failure throws `CRITICAL_TRANSACTION_ACK_UNCONFIRMED` with `commitState='committed'`, `committed=true`, `acknowledgmentState='unknown'`, `retryable=false`, and the transaction UUID. An uncertain database publication uses `commitState='uncertain'` and `committed=null`. The boundary never rolls back an already published database or repeats the callback. Credential refresh preserves these fields and cannot turn an unknown receipt into success by comparing credential content. Repository settings, connection, and quarantine wrappers invoke their transaction once; they do not retry the mutation.

`recoverCriticalAcknowledgment({databaseFile, db, transactionId})` publishes only a missing receipt, or rechecks and fsyncs the identical existing receipt. Supply a read-only connection to the durable database under verified single-writer ownership. Recovery validates the immutable marker, epoch and original intent. It never modifies a business row or redeems credentials. Failed-attempt evidence remains retained after recovery. Snapshot backups must preserve the marker tables; restoring a database behind an existing receipt sequence is rejected before the callback.

Root schema registration consumes the single `CRITICAL_ACK_TABLES` and `CRITICAL_ACK_TRIGGERS` exports in `src/lib/db/criticalAckSchema.js`. Adapter initialization does not create a journal. The first critical transaction bootstraps those same definitions atomically for adapters used without the repository migration runner. Database marker UPDATE/DELETE operations are rejected by triggers.

## Observation contract

`captureCriticalAcknowledgments({databaseFile, db, maxRecords=100000})` reads the retained journal and marker population without writing. Pass the observer's read-only database snapshot connection. It reports explicit failures or unobservable states for missing sources, gaps, unknown build identity, corrupt rows, changed capture boundaries, unsafe permissions, and exceeded bounds. The journal includes all receipts, intents, failure records, its epoch header, and the sorted filename/digest inventory whose hash is `journal.sha256`. No receipt is silently omitted to meet the bound.

The collector must revalidate the complete capture with `validateCriticalAcknowledgmentCapture`, bind it inside the signed observation envelope, and reconcile begin/end retained receipts against the final immutable database markers. The validator independently derives hash continuity, source joins, inventory, process identities and counters. It does not trust supplied clean flags. Historical failed intents with a confirmed rollback remain visible; unresolved intents prevent a complete capture. Whole-window identity and natural-traffic gates remain the collector's responsibility.

`getCriticalAcknowledgmentRuntime({databaseFile})` must run inside the backend process. It supplies the stable process UUID/PID, instrumentation enablement timestamp, build SHA, observed drivers and monotonic counters. `omittedAttempts` records failure paths that could not retain an external failure record, including storage errors before intent publication. The read-only observer's process identity is separate. A complete window needs backend identity/enablement/counter coverage; an empty observer snapshot is not proof that no acknowledgment was lost. Build identity uses the artifact-inlined `TP_BUILD_SHA`, falling back to the artifact working directory's `BUILD_SHA`; missing identity remains null.

## Retention and execution limits

No automatic pruning or rotation deletes evidence, so a 24-hour window remains available across restarts. Retention consumes at least two small files plus one marker per successful critical transaction. Capture scans retained history and currently has an explicit 100,000-marker bound. Higher-volume retention and indexed window capture need a separately verified archival contract; exceeding this bound cannot qualify a release.

Critical writes add synchronous journal I/O and marker/index maintenance. Native writes add intent and receipt file/directory barriers; the first transaction also creates the epoch header. sql.js retains its whole-database export cost. Measure these costs on the integrated candidate before release.

sql.js uses in-memory snapshots and requires one verified writable owner for a database file. Concurrent writable sql.js adapters can overwrite each other's snapshots on ordinary flushes; this change detects missing acknowledged markers but does not establish an interprocess writer lease. Concurrent-writer qualification remains unavailable until that separate ownership contract is implemented. Analytics observers must use read-only database access.

Windows lacks the directory fsync barrier used here and its captures report `directory-fsync-unavailable`; a successful file flush alone does not qualify equivalent power-loss durability. Node/better-sqlite3/sql.js focused tests exercise actual temporary databases, injected storage failures, immutable markers, restart reconciliation, receipt-only recovery, and owned child exits on both sides of the receipt barrier. Application builds, production execution and sustained-load qualification remain separate gates.

Run the focused Node suite from `tests/` with `node node_modules/vitest/vitest.mjs run unit/critical-ack-journal.test.js unit/refresh-runtime-persistence.test.js unit/sqljs-atomic-persist.test.js unit/db-driver-chain.test.js --maxWorkers=1`. Run the Bun-specific adapter check from the repository root with `bun tests/qa/critical-ack-bun.mjs`; it creates and removes only its own temporary fixture directory.

Filesystem and SQLite barrier semantics follow the [Node 24 filesystem API](https://nodejs.org/docs/latest-v24.x/api/fs.html) and [SQLite synchronous pragma](https://www.sqlite.org/pragma.html#pragma_synchronous).

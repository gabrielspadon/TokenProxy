# Versioned routing configuration

This foundation covers combo definitions and ordered members, model aliases, and selected combo settings. It excludes account credentials, keys, provider endpoints, proxy configuration, disabled-model scopes, and shaping options. Configuration rollback, database restoration, and release rollback remain different operations.

Snapshots retain only combo IDs/names/kinds/member identifiers, direct model-alias targets, comboStrategy, comboStickyRoundRobinLimit, exposeComboOnly, and per-combo fallbackStrategy/judgeModel/memberConnections/fusionTuning. Other settings and per-combo shaping properties remain in the existing store and are preserved during activation. An omitted covered property restores the existing gateway default through its normal settings reader.

The selected document has one recursively canonical hash. Object keys and combo records are ordered deterministically; member arrays retain their declared order. The expectedCurrent token is the hash of the actual covered store, not a cache. Legacy direct writers capture before and after in their existing SQLite transaction. Draft revisions and published snapshots are immutable append-only records; only the draft head pointer changes. Draft edits require expectedRevision.

The new operator API follows the existing requireAdmin policy. Reads require an operator credential; writes additionally require a loopback request. It records verified operator class rather than inventing an operator identity. Legacy route provenance is explicitly unverified because its existing authentication policy remains unchanged. No credential value, HTTP authorization header, arbitrary provider error, or free-form provenance is retained.

Saving a draft does not change effective routing. Validation uses the gateway's combo-cycle and model-resolution helpers plus current local custom/free/static catalog evidence. Aliases are direct provider/model targets, matching actual one-hop routing; alias chains/cycles are rejected, not added as a new routing capability. Qualified provider/model identifiers are declarations, not proof of upstream support. Account member bindings must name an existing account of the resolved provider. Validation never probes a provider.

Activation revalidates the exact draft revision. A durable staged receipt precedes the synchronous SQLite transaction that compares expectedCurrent, writes the covered existing stores, and records the new configuration version. All database writes and the applied receipt commit together. In-process combo rotation invalidation follows persistence. Failure before commit leaves routing unchanged and records failure; failure after commit records a partial outcome with the effective configuration hash. A remaining staged receipt after interruption means completion is unknown and is not retried automatically. Rollback applies a prior immutable document through the same mechanism and creates a new version and receipt.

The alternative of versioning all settings was rejected because those settings include credentials and runtime/network side effects. A separate policy database was rejected because optimistic activation would not be atomic with the actual gateway store. This implementation uses the existing SQLite adapter and store semantics, with explicit coverage limits rather than asserting whole-install restoration.

Acceptance uses the real SQLite adapter and repository reads for draft/save/validate/activate/conflict/rollback/audit. It also covers concurrent revision/current conflicts, malformed and secret-bearing input, unchanged outside-scope settings, ordered member hashes, database rollback, runtime partial failure, and operator/auth-class refusal. No production data or upstream model calls are part of these checks.

## API

The operator namespace is `/api/admin/configuration`. Every response uses `Cache-Control: no-store`. `GET /` returns the current covered document, `currentHash`, coverage and local validation. `GET /versions` and `/receipts` accept bounded `limit` and integer `before` cursors; `/drafts` uses a UUID `before` cursor. `GET /versions/{id}` and `/drafts/{id}` return one immutable version or current draft head, respectively.

`POST /drafts` accepts `{document, expectedCurrent}`. `PATCH /drafts/{id}` accepts `{document, expectedRevision}`. `POST /drafts/{id}/validate` accepts `{expectedRevision}`. `POST /drafts/{id}/activate` accepts `{expectedRevision, expectedCurrent}`. `POST /versions/{id}/rollback` accepts `{expectedCurrent}` and refuses draft versions. Hashes and revisions are required, never inferred from a stale read. Refusal codes distinguish malformed requests (400), authentication/authorization (401/403), missing records (404), optimistic conflicts (409), and locally invalid activation (422). A committed configuration with failed runtime refresh returns 207 and `outcome: partial`; success returns 200. Oversized input is rejected at 256 KiB before JSON parsing. No body or raw exception is logged.

History APIs expose no update/delete operation for versions or receipts. Append-only immutability is enforced by the repository contract; an operator with direct database write access can still alter the database. Snapshot rows are redacted whitelisted projections, not credential backups. Malformed legacy values that cannot be represented safely remain visibly invalid in local validation and cannot be activated until repaired in a new draft. Direct SQL, imports, disabled-model mutations, and catalog edits are outside the existing-writer hooks. Current hashes are always computed from the actual covered tables so out-of-band covered changes still defeat a stale activation.

SQLite commit boundaries follow the existing adapters' synchronous transaction contract. SAVEPOINT release inside an outer transaction is not independent durable publication, so configuration APIs must own their outer transaction; they are not called from another repository's transaction. Other processes observe committed configuration, but their in-memory rotation counters are not reset by this process. Existing in-flight requests and process-local state remain outside restoration. See [SQLite transactions](https://www.sqlite.org/lang_transaction.html), [savepoints](https://www.sqlite.org/lang_savepoint.html), and [isolation](https://www.sqlite.org/isolation.html).

The sql.js adapter exposes an explicit synchronous `flush()` barrier for draft writes and staged publication. It writes a mode-600 same-directory temporary file, fsyncs the file, atomically replaces the database, and fsyncs the parent directory on POSIX. Windows performs the file fsync without a directory fsync. Other adapter callers retain their existing debounce. Stage-flush failure prevents configuration writes; a later flush failure reports partial with in-memory configuration retained and disk persistence unconfirmed. Successful native SQLite transactions use their existing commit durability. sql.js is a process-local database image and is not a supported multi-process shared-file writer.
